After [running a 40B MoE at 120k context](/en/posts/flint-40b-moe-6gb-vram/) on this same laptop, I wanted the opposite: a small model that fits **entirely** on the GPU, with a huge context, that I could use every day without the machine noticing.

All of this runs on a **laptop**: the GPU is an **RTX 3050 Laptop** with 6 GB of VRAM, the mobile version, more power-limited than the desktop card, and it also draws the system desktop, so the full 6 GB are never free. Liquid AI's LFM3-1.7B promises 256k tokens of context and is built for agents and tool calling. I measured it from 0 to 200k tokens, in its official release and two uncensored variants, and compared it with three models that, on paper, should also fit.

## Summary

- **On a laptop RTX 3050 (6 GB), LFM3-1.7B is the only one of the four models that fits at 200k and still works well there**: 4.3-4.5 GB of VRAM, 35-40 tok/s generation with the context full, near-perfect long-context recall (59/60 across its four versions) and 35/35 on tool calls in every one of them.
- **The official release is the best general choice**: Liquid's Q6_K generates fastest (101 tok/s empty) and is the fastest agent. The uncensored variants lose no quality in these tests, but they don't gain any either.
- **CUDA, not Vulkan**: on the same card, CUDA reads the context about 8 times faster and does not freeze the desktop.
- **Reasoning stays on.** Without it the output breaks. But it spends a lot of tokens on some tasks, so give it room.
- **It works as a read-only subagent** (code search, reading memory, answering with citations). **It does not work for editing code**: in one test it broke an import and reported that the test had passed.

## The model

LFM3-1.7B is a **hybrid**: almost all of its layers are short convolutions and only a few use attention. That matters because the KV cache (the context memory) only grows in the attention layers, so 200k tokens fit in little memory. A full-attention model of the same size could not fit a 128k KV cache even compressed.

It ships with reasoning ("thinking") on by default, and Liquid recommends keeping it that way. I tested four versions: Liquid's official release in two quantizations, and two community "abliterated" variants (with the original training's refusals removed) at those same quantizations so they can be compared:

| Version | File | Size | In the tables |
|---|---|---|---|
| Liquid official | `LFM3-1.7B-Q6_K` | 1.43 GB | **Official Q6** |
| Liquid official | `LFM3-1.7B-Q8_0` | 1.85 GB | **Official Q8** |
| AtomicChat Uncensored | `AD-Q6_K` | 1.6 GB | **AD** |
| Vortecks Heretic-Abliterated | `Q8_0` | 1.8 GB | **Heretic** |

## LFM3 speed with CUDA

Tokens per second, mean of 3 runs:

| Context filled | Official Q6 pp / tg | AD pp / tg | Official Q8 pp / tg | Heretic pp / tg |
|---|---|---|---|---|
| 0 | 5183 / **101** | 5107 / 90 | 5803 / 81 | 5784 / 80 |
| 8k | 4598 / 95 | 4678 / 87 | 5138 / 77 | 5001 / 76 |
| 32k | 3466 / 81 | 3547 / 74 | 3606 / 66 | 3648 / 66 |
| 64k | 2567 / 67 | 2593 / 63 | 2721 / 57 | 2681 / 57 |
| 128k | 1676 / 50 | 1690 / 47 | 1745 / 44 | 1745 / 44 |
| 200k | 1231 / **40** | 1171 / 38 | 1262 / 36 | 1260 / 35 |

Reading 200k tokens in one go takes about **a minute and a half**. VRAM stays at 4.3-4.5 GB at 200k, with the desktop on the same card. The Q6_K files generate faster because they are smaller; the Q8_0 files read a bit faster. Between the two Q6_K files, the official one generates 10 % faster than AtomicChat's; between the two Q8_0 files, official and Heretic are practically identical.

### Batch size barely matters

With Flint, raising `-ub` to 2048 doubled prompt processing, because the experts travelled over PCIe on every batch. Here nothing travels: the whole model is on the GPU. Reading 4096-token blocks (measured with AD and Heretic):

| pp4096 (tok/s) | ub 512 | ub 1024 | ub 2048 |
|---|---|---|---|
| AD, empty | 5134 | **5243** | 5188 |
| AD, 128k | 1705 | **1757** | 1710 |
| Heretic, empty | 5683 | **5925** | 5466 |
| Heretic, 128k | 1758 | **1772** | 1702 |

1024 wins by 2-4 %. `-ub 4096` no longer fits in VRAM at 128k.

## CUDA vs Vulkan on the same card

On the RTX 3050, Vulkan generates almost as fast as CUDA, but reads the context **about 8 times slower**: 13 minutes for 200k tokens versus a minute and a half. And there is a detail that matters more than speed on a laptop: on my machine the NVIDIA card also draws the desktop. With Vulkan at 100 % the desktop freezes until it finishes; with CUDA, at the same 100 %, I can keep using the machine normally.

> [!NOTE]
> I ran this comparison with two different llama.cpp builds (one two weeks old, one from the day before). Later I consolidated everything into a single llama.cpp checkout with both variants, but I did not repeat Vulkan on the NVIDIA card: the gap is so large, and the frozen desktop so annoying, that I will not use it.

## The integrated GPU (Radeon 660M, Vulkan)

The Radeon 660M uses system RAM (1 GB reserved plus up to 15 GB shared). It is a fallback when the NVIDIA card is busy, and it does not touch the desktop:

| Context filled | AD pp / tg | Heretic pp / tg |
|---|---|---|
| 0 | 500 / 38 | 573 / 33 |
| 8k | 409 / 34 | 459 / 31 |
| 32k | 261 / 28 | 288 / 26 |
| 64k | 180 / 22 | 194 / 21 |
| 128k (1 run) | 83 / 16 | 86 / 15 |

Fine for chatting; not for long documents. And it does not handle several jobs at once: with three processes using it at the same time it dropped to about 2 tok/s.

## Does it really use the 200k?

I hid a sentence with a made-up code inside *Don Quixote* (Project Gutenberg, public domain) at 10, 50 and 90 % of the text, and asked for the code in Spanish.

| Context | Official Q6 | Official Q8 | AD | Heretic |
|---|---|---|---|---|
| 8k | 3/3 | 3/3 | 2/3 (then 10/10 with 10 seeds) | 3/3 (10/10) |
| 32k | 3/3 | 3/3 | 3/3 | 3/3 |
| 64k | 3/3 | 3/3 | 3/3 | 3/3 |
| 128k | 3/3 | 3/3 | 3/3 | 3/3 |
| 200k | 3/3 | 3/3 | 3/3 | 3/3 |

It answered in Spanish every time. Heretic also tends to say which chapter it found the note in.

> [!NOTE]
> In my first long-context test I used English software licence texts as filler, and the model answered in English and only summarized the end. With a Spanish text the problem went away: the filler matters.

|---|---|---|---|---|

| Calculator with an expression | 5/5 | 5/5 | 5/5 | 5/5 |
| Picking the right tool out of seven | 5/5 | 5/5 | 5/5 | 5/5 |
| Two parallel calls | 5/5 | 5/5 | 5/5 | 5/5 |
| Not using a tool when none is needed | 5/5 | 5/5 | 5/5 | 5/5 |
| Email with three arguments | 5/5 | 5/5 | 5/5 | 5/5 |
| Multi-step agent (find a file, read it, count and write the result) | 5/5 (**10 s**) | 5/5 (14 s) | 5/5 (16 s) | 5/5 (12 s) |

For what Liquid designed it for, all four versions are flawless: 140 out of 140. The official Q6_K solves the agent task fastest.

## Reasoning: don't turn it off, give it room

LFM3 reasons before answering, and how much it reasons depends on the **type of task**, not on the size of the text:

| Task | Measured reasoning |
|---|---|
| Finding one fact (needle) | ~150 tokens |
| Tools and agent | 100-1400 tokens |
| Enumerating across a long text | ~6600 tokens |
| Summarizing a conversation | ~11,600 tokens |

With low `max_tokens`, the last two run out of budget while reasoning and **never answer**. The fix is to allow up to 16k tokens and ask in the prompt for brief reasoning. Turning it off is not an option: I tried `enable_thinking=false` to find errors in an 85k-token log. It took 2 minutes instead of 7, but the output was broken (empty citations). Liquid warns about this, and I confirmed it.

### Loops in free-form prose

Without a system prompt and with free writing, it sometimes gets stuck reasoning in a loop. I measured 10 repetitions per combination:

| Prose loops (out of 10) | Official Q6 | Official Q8 | AD | Heretic |
|---|---|---|---|---|
| temp 0.1 with system prompt | 1 | 2 | **0** | 1 |
| temp 0.1 without system prompt | 3 | **0** | 2 | 2 |
| temp 0.6 with system prompt | 3 | 3 | 2 | **0** |
| temp 0.6 without system prompt | 1 | 3 | 3 | 2 |

The structured JSON task had **no loops at all** in 160 responses, and all 160 JSON outputs were valid. Three practical takeaways:

- **The loops come from the model**, not from the uncensoring: the official release falls into them as much or slightly more.
- **There is no magic temperature**: the best combination changes from version to version, and with 10 repetitions the differences (0 to 3 loops) are small. The system prompt helps in most cases.
- **Structured tasks are no problem at all.** If you need free-form prose, give it plenty of token budget and check the output.

## The rivals

I looked for models that, on paper, should also fit in 6 GB with 128k context: all hybrids or with few attention layers. Same tests, same engine (CUDA).

### Generation speed (tg, tok/s)

| Context filled | LFM3 official Q6 | LFM3 official Q8 | Jamba 3B | Nemotron 4B | Qwen3.5 4B* |
|---|---|---|---|---|---|
| 0 | **101** | 81 | 72 | 56 | 49 |
| 32k | **81** | 66 | 70 | 47 | 26 |
| 64k | 67 | 57 | **69** | 41 | 17 |
| 128k | 50 | 44 | **66** | out of memory | out of memory |
| 200k | 40 | 36 | **64** | out of memory | out of memory |

\*Qwen3.5 with a compressed KV cache (`-ctk q8_0 -ctv q4_0`), the only way it fits.

Jamba is the most interesting on speed: with only 2 attention layers out of 28, it **barely slows down** as the context fills (72 → 64 tok/s), while LFM3 drops from 101 to 40. But speed does not help if the answer is useless.

### Quality

| Model | Needle 8k | 32k | ~64k | 128k-200k | Tools |
|---|---|---|---|---|---|
| **LFM3 (all four versions)** | ✅ 11/12 | ✅ 12/12 | ✅ 12/12 | ✅ 24/24 | **35/35** each |
| Qwen3.5 4B | 3/3 | 3/3 | 3/3 | does not fit | **35/35** (agent in 9 s) |
| Nemotron 3 Nano 4B | 3/3 | 0/3 | 0/3 | does not fit | 28/35 (parallel 0/5) |
| Jamba Reasoning 3B | 3/3 | 1/3 | 0/3 | 0/6 | 24/32 (fails irrelevance and agent) |

- **Jamba** collapses from 32-64k on: broken `<think>` tags, repeated line breaks and even a chunk of unrelated JavaScript. I re-ran the long cases with AI21's recommended sampling (temperature 0.6, no penalty) and it collapsed the same way. I cannot tell whether it is the model or its llama.cpp support; this data cannot separate the two.
- **Nemotron** returns an empty answer from 32k on, after a few words of reasoning. That smells like a template or support problem rather than the model's memory: I am calling it **inconclusive**.
- **Qwen3.5-4B** recalls perfectly where it fits and is as good an agent as LFM3, but in 6 GB it does not go past about 64k, and at that point it generates at 17 tok/s.

> [!WARNING]
> The theoretical VRAM estimates were wrong for both 4B models: on paper, Nemotron and Qwen3.5 fit at 128k. In practice, with the desktop on the same card, neither started. Measure before trusting a table.

## Real use

I wired it into my workflow and tested it live:

- **Long-context coding agent** (pi): loads in 3 seconds with 200k of context, and reads the persistent memory of past projects **read-only**. I asked it about a decision made hours earlier; it searched, and answered citing the right memory in 12 seconds.
- **Search subagent** (questions about a repository, with `file:line` evidence): 2 min 25 s with CUDA versus 12 min 29 s on the integrated GPU. All six citations were correct.
- **Pre-digesting long text** (logs, build output) before handing it to a cloud model: accurate, but slow on big inputs. It found the two exact lines in an 85k-token log, but took 7 minutes, almost all of it reasoning. To find the word `ERROR`, `grep` still wins.

> [!FAIL]
> As a subagent that **edits** code it does not work. I asked it to rename a constant across four files. It misspelled the name in the definition (breaking the import), added a comment I did not ask for, and **reported that the verification command had passed**. It had not. A typo is tolerable; a false report is not. Liquid already says it is not recommended for agentic coding, and I locked it to read-only tasks.

## What went wrong (and how I caught it)

The method mistakes most useful to anyone repeating this:

- **The `-ub` sweep with `-p 512`**: with a 512-token prompt the batch never exceeds 512, so every option looked the same. Use a prompt longer than the batch.
- **The invisible hyphen**: Heretic wrote the code with a non-breaking hyphen (U+2011) instead of a normal one, and my check marked correct answers as failures. Normalize hyphens before comparing.
- **Split context**: with an explicit `-np 3`, llama.cpp does not share the KV cache across slots, and each one gets a third of the context (43k of 131k). You need `--kv-unified`.

## The final command

```bash
llama-server -m LFM3-1.7B-Q6_K.gguf \
  --device CUDA0 -ngl 99 -fa on -c 204800 -np 1 -ub 1024 \
  --cache-ram 2048 --no-context-shift \
  --jinja --reasoning on \
  --temp 0.1 --top-k 50 --repeat-penalty 1.1 \
  --host 127.0.0.1 --port 8091
```

- This is the official Q6_K, the fastest. If you need it to never refuse, the uncensored variants work just as well in these tests.
- Without `--device`, llama.cpp splits the model between the NVIDIA card and the integrated GPU.
- Do not set `--reasoning-budget`: Liquid says the model is not trained for it. Raise `max_tokens` instead.
- If you will serve several requests at once, add `-np N --kv-unified`.

## Conclusions

If you have a 6 GB laptop GPU and need **real long context**, LFM3-1.7B is, today, the option that works, and the official release is the best starting point: it fits whole at 200k, reads a book in a minute and a half, remembers what it read and uses tools without failing. It is not a model for thinking through hard problems or writing code on its own. It is a fast, cheap and private reader, and in that role no rival beat it on this card.

The numbers come from one machine, with specific versions of llama.cpp and of each model (the ones in the table above). With other versions, especially for Jamba and Nemotron, the results could change.
